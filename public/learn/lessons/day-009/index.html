Prompting and context

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
A prompt is not a magic command. It is part of the model's current context. Clear instructions, relevant evidence, useful examples and explicit constraints make the intended task easier to infer and execute.

1. Prompting works through context

Yesterday, we saw that a large language model predicts the next token using the context available to it.

A prompt is part of that context. It can contain instructions, questions, examples, source material, formatting requirements and constraints.

The model does not read the prompt as a legal contract. It processes the prompt as tokens and uses learned patterns to generate a continuation that appears to satisfy the request.

2. Clear task instructions reduce ambiguity

Vague instructions leave more of the task unspecified.

Summarise this does not specify audience, length, emphasis or format.

A more precise instruction might say: Summarise this report for a non-technical manager in five bullet points. Include the main risk and recommended next action.

The second prompt is not better because it is longer. It is better because it removes important ambiguity.

3. Relevant context supplies missing information

If a task depends on specific facts, policies, documents or circumstances, those need to be available to the model.

Asking for a summary of a private document without providing the document gives the model no reliable access to its contents.

Good context engineering therefore includes deciding what evidence should be supplied, not simply finding clever wording.

4. Examples can demonstrate the desired pattern

Sometimes a task is easier to specify by showing an example.

This is often called few-shot prompting when one or more examples are included.

Examples can demonstrate tone, output structure, classification rules or treatment of edge cases.

A misleading example can teach the wrong pattern, so examples need to represent the behaviour you actually want.

5. Constraints define boundaries

Constraints tell the model what limits matter.

They can specify output length, required fields, forbidden actions, acceptable sources, language, tone or what to do when information is missing.

For factual work, a useful constraint is: If the supplied evidence does not support the answer, say that the information is insufficient.

This does not guarantee perfect compliance, but it gives the model a clearer target behaviour.

6. Structure separates instructions from data

Prompts become easier to interpret when sections have clear boundaries.

Headings, labels, quotation marks, Markdown fences or XML-style tags can distinguish instructions from source material.

Task:
Summarise the source in three bullet points.

Source:
<document>
...source text...
</document>

Rules:
- Use only information in the source.
- If a fact is missing, say so.

The exact delimiter style matters less than making the structure clear and consistent.

7. Output format can be explicit

If software must process a response, format matters.

You might request a table, fixed headings or structured JSON rather than free-form prose.

For human-facing work, a shape such as Problem → Evidence → Recommendation can improve consistency.

When an API offers schema-constrained structured output, that is generally stronger than relying on prompt wording alone to enforce machine-readable structure.

8. Prompting is iterative, not mystical

Prompt engineering is sometimes presented as finding one perfect phrase. That is the wrong mental model.

A better process is: define the task, test the output, identify failure modes, improve the instructions or context, then test again.

If repeated failures come from missing evidence, rewriting the same instruction will not solve the real problem. The context or system design must change.

9. Context engineering is broader than prompt wording

Context engineering is a broader term for deciding what the model should see when it performs a task.

That can include system instructions, user input, retrieved documents, tool outputs, examples, memory summaries and metadata.

This is an architectural concern as well as a writing concern. Later, retrieval and agent systems will actively assemble context before asking the model to respond or act.

Worked example: extracting decisions from meeting notes

Suppose you want an AI system to extract decisions from meeting notes.

Weak request
Read these notes and tell me what matters.
Better specified request
Return only confirmed decisions. For each give: decision, owner, deadline. If owner or deadline is absent, write "Not specified". Do not infer missing facts.

The stronger version defines the task, output shape and missing-information rule.

If the notes are then provided in a clearly marked source section, the model has both instructions and evidence.

Why this matters

Prompting sits between raw model capability and useful application behaviour.

Clear prompts improve the chance that the model understands the task, but prompts do not create missing facts, permissions or reliable external state.

Robust AI systems therefore combine prompting with retrieval, tools, structured data, validation and deterministic controls.

Key terms

PromptInstructions and information supplied as part of the model's current context.
ContextThe tokenised information available to the model during an operation.
ConstraintAn explicit boundary or requirement on output or behaviour.
Few-shot promptingIncluding examples to demonstrate a desired pattern.
DelimiterA marker used to separate prompt sections.
Output formatThe requested structure of the response.
Context engineeringDesigning the information supplied to a model for a task.
Failure modeA recurring way a system produces an undesirable result.
