How APIs connect software

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
An API is a defined interface that lets one piece of software request data or capabilities from another. The caller sends a request in an agreed format; the API processes it and returns a response. The contract matters more than the implementation hidden behind it.

1. API means Application Programming Interface

An API is an interface designed for software to interact with software.

It defines what operations are available, what inputs are expected, what outputs can be returned and what rules the caller must follow.

APIs exist in many forms. Today's lesson focuses mainly on web APIs, where applications communicate over HTTP.

2. An endpoint identifies where a request goes

A web API usually exposes one or more endpoints.

An endpoint is a specific address, often a URL path, that represents a resource or operation.

For example, an imaginary weather service might expose /forecast and /locations.

The exact endpoint names are defined by the API provider; they are not universal conventions.

3. HTTP methods express the intended operation

HTTP requests include a method that communicates the intended action.

GET is used to retrieve a representation of a resource. POST submits data to a resource and often causes processing or a change in server state.

Other common methods include PUT, PATCH and DELETE.

The method is part of the API contract: a URL alone does not fully describe a request.

4. A request carries more than a URL

An HTTP API request can include a method, URL, headers, query parameters and sometimes a request body.

Headers carry metadata such as content type or authentication information.

Query parameters are values attached to a URL, while a request body can carry larger or more structured input.

Different APIs define which fields are required and where they belong.

5. JSON is a common API data format

Many web APIs exchange structured data using JSON, the format introduced on Day 4.

{
  "city": "Leeds",
  "units": "metric"
}

The API documentation defines what keys are allowed, which are required and what value types they accept.

JSON is common, but APIs can use other formats too.

6. Responses contain status, headers and usually data

The server returns an HTTP response after processing the request.

The response includes a status code. A 200 OK response indicates success, while other codes describe creation, client errors or server errors.

The response may also contain headers and a body containing JSON, text, binary data or another representation.

Good application code checks the response status rather than assuming every request succeeded.

7. Authentication controls who may use an API

Many APIs require credentials before accepting a request.

Common mechanisms include API keys, access tokens and OAuth-based flows.

Credentials should be treated as secrets. Putting a private API key directly into browser-delivered JavaScript can expose it to users.

A common architecture is therefore browser → your server → external API, with the secret stored server-side.

8. Errors are normal engineering cases

Network calls can fail because of invalid input, missing authentication, rate limits, unavailable services, timeouts or connectivity problems.

Robust software handles these possibilities deliberately.

That can mean validating input, checking status codes, retrying only when appropriate, recording useful diagnostics and showing a clear fallback.

An API integration is not complete just because the successful case works.

9. AI applications commonly call models through APIs

An AI model can be offered as an API capability.

Your application sends model input, such as instructions and context, to an API endpoint. The provider runs inference and returns output that your application can process.

The model API does not automatically control your whole application. Your code still decides when to make the request, what information to send, what to do with the response and whether any resulting action is permitted.

Worked example: a website that summarises text

Imagine a website where a user pastes a report and presses Summarise.

User submits report
Server validates input
Server calls model API
API returns response
Website displays summary

The server might send a POST request containing the prompt and report text as structured data. The model provider performs inference and returns a structured response.

The website checks that response, extracts the output and displays it. If the API rejects the request or times out, the application needs a separate error path.

This connects Days 5, 8 and 9: deterministic software controls the workflow, the language model generates content, and the prompt becomes part of the API request.

Why this matters

APIs are one of the main ways separate software systems are composed into useful products.

Weather data, payments, maps, email services, databases and AI models can all be exposed through APIs.

Understanding requests, responses, authentication and failure handling lets you see an AI feature as an ordinary software integration rather than a mysterious capability embedded inside a page.

Key terms

APIA defined interface that allows software systems to interact.
EndpointA specific API address representing a resource or operation.
HTTP methodA request method such as GET or POST describing the intended operation.
RequestThe message a client sends to an API.
ResponseThe message the server returns after processing a request.
Status codeA numeric HTTP result describing the outcome of a request.
AuthenticationThe process of establishing that a caller may access a capability.
API keyA credential some APIs use to identify or authorise a caller.
