Retrieval-augmented generation

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
Retrieval-augmented generation, or RAG, is a system pattern: first retrieve relevant external information, then place that information into the language model's context before generation. Retrieval can improve grounding, but only if the right evidence is found and the model uses it correctly.

1. RAG combines retrieval with generation

Yesterday, we learned how embeddings can help software find meaning-related information.

Retrieval-augmented generation, usually shortened to RAG, connects that retrieval step to a generative model.

The application searches an external knowledge source, selects relevant evidence, adds that evidence to the model's context, then asks the model to produce an answer.

RAG is therefore not a new kind of model. It is an application architecture built around a model.

2. Retrieval happens before the final answer

A basic RAG pipeline starts with the user's question.

The system turns that question into a search query, retrieves relevant passages, then constructs a prompt containing both the question and the retrieved evidence.

The language model generates its response from that augmented context.

This gives the model access to information that may not be available from its trained parameters alone.

3. The knowledge source can be private, specialised or newer

RAG is useful when an application needs information from documents, databases, support articles, policies, product catalogues or other external sources.

Those sources can contain private organisational knowledge, specialist material or information that changed after model training.

The application still has to decide which sources are searchable and what the user is permitted to retrieve.

4. Retrieval can use semantic, keyword or hybrid search

Embedding-based semantic search is common in RAG, but it is not the only retrieval method.

Keyword search can be better for exact names, identifiers or rare terms. Semantic search can be better when wording differs but meaning is similar.

Many systems use hybrid search, combining lexical and semantic signals, then optionally reranking the candidates.

RAG quality depends heavily on retrieval quality.

5. Top-k controls how many passages are retrieved

Retrieval systems often return the top k matches: for example, the three or five passages judged most relevant.

Retrieving too few can miss necessary evidence. Retrieving too many can add noise, increase token use and crowd the context.

There is no universal best value. It should be tested against the actual documents and questions the system must handle.

6. Reranking can improve the candidate set

A first-stage search can retrieve a broader set of likely matches.

A reranker can then score those candidates more carefully and reorder them before the best passages are placed into the prompt.

This separates fast retrieval from more expensive relevance judgement.

7. Grounding connects the answer to supplied evidence

When a model is instructed to answer from retrieved sources, the goal is often described as grounded generation.

The system can ask the model to use only the supplied evidence, cite source passages and say when the evidence is insufficient.

This can reduce unsupported claims, but it does not guarantee correctness.

The source may be wrong, or the model may misread or ignore it.

8. RAG has two major failure surfaces

A useful distinction is retrieval failure versus generation failure.

If the correct evidence never reaches the model, retrieval failed.

If correct evidence is present but the model still answers incorrectly, the generation or prompting stage failed.

These require different fixes, so evaluation should inspect both retrieved passages and final answers.

9. Permissions and source quality belong in retrieval

Semantic similarity alone is not enough to decide what should be retrieved.

A business system may need filters for user permissions, document status, date, department or source authority.

Retrieval must not expose a private document merely because its vector is close to the user's query.

Access control belongs in the retrieval architecture, not in a model guess.

Worked example: answering a staff policy question

Suppose an employee asks, “How much notice do I need to give for annual leave?”

User question
Search policy chunks
Rank passages
Build context
Generate answer
Return source

The system searches approved policy documents rather than asking the model to rely on memory.

If the current policy contains the answer, that passage is supplied to the model as evidence.

The application can instruct the model to answer only from the retrieved policy and to say when the policy does not contain the requested information.

If the wrong policy version is retrieved, the answer can still be wrong even if the model follows the prompt perfectly.

Why this matters

RAG is one of the most important patterns for building AI systems around real information.

It separates model capability from application knowledge: the model provides language capability, while the application supplies selected evidence at runtime.

This makes it possible to update the knowledge source without retraining the model, but it creates engineering responsibilities around indexing, permissions, retrieval quality, source freshness and evaluation.

Key terms

RAGRetrieval-augmented generation: retrieving external information and adding it to model context before generation.
GroundingConnecting generated output to supplied evidence or trusted sources.
Top-kThe number of highest-ranked retrieval results returned.
Hybrid searchRetrieval combining lexical and semantic search signals.
RerankingRescoring retrieved candidates to improve their relevance order.
Retrieval failureFailure to find or supply evidence needed for the task.
Generation failureFailure to use available evidence correctly when producing an answer.
Knowledge sourceThe external documents, records or data searched by the retrieval system.
