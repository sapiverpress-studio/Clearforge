Automation and orchestration

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
Automation performs predefined work when a trigger occurs. Orchestration coordinates multiple steps, services and decisions into a controlled workflow. Reliable systems keep predictable work deterministic and use AI only where judgement or interpretation genuinely adds value.

1. Automation starts with a trigger

An automation begins when something tells the system that work should start.

A trigger might be a schedule, a button press, a new database record, an incoming API request or a webhook sent by another service.

The trigger should contain or identify enough information for the workflow to know what event occurred and what should happen next.

2. A webhook is an event delivered over HTTP

A webhook lets one system notify another when a subscribed event occurs.

Instead of repeatedly asking, “Has anything changed?”, the receiving application exposes an HTTP endpoint and the sending service posts an event payload to it.

Webhook handlers should verify authenticity where the provider supports signed deliveries, validate the payload and avoid assuming every delivery is unique.

3. Orchestration coordinates the whole workflow

Orchestration is broader than one automated action. It controls the order and conditions under which several steps run.

A workflow might validate input, save a record, call an API, wait for a result, branch on the outcome and notify a user.

The orchestrator is responsible for knowing which stage the workflow has reached and what should happen after success or failure.

4. Keep deterministic steps deterministic

If a rule can be expressed reliably in ordinary code, an LLM usually should not decide it.

Checking whether an invoice total exceeds £1,000 is a deterministic comparison. There is no benefit in asking a probabilistic model to guess the answer.

AI is more appropriate for tasks such as classifying ambiguous text, extracting meaning from messy input or drafting content that still sits inside controlled workflow rules.

5. Queues decouple producers from workers

A queue stores work items until a worker is ready to process them.

This separates the component that creates work from the component that performs it. A website can accept a request quickly while slower processing happens elsewhere.

Queues also help absorb bursts of work and support retry behaviour when a worker or downstream service is temporarily unavailable.

6. Delivery can happen more than once

Many distributed queue systems use at-least-once delivery. That means a message should be delivered, but under some conditions the same message can arrive more than once.

That is why important handlers should often be idempotent: processing the same event twice should not create an unintended duplicate effect.

A payment-confirmation handler should not issue two receipts or two fulfilment requests just because a message was retried.

7. Retries need limits and backoff

A temporary network failure may succeed on a later attempt, so retries are useful.

But immediate unlimited retries can overload a struggling service and increase cost. Systems commonly limit retry counts and wait progressively longer between attempts.

Permanent failures should eventually leave the normal retry path and become visible for investigation or recovery.

8. Human approval belongs before consequential actions

Automation does not mean every step should run without human control.

A workflow can prepare a high-impact action, pause, present the relevant evidence and wait for a named person to approve or reject it.

This is especially useful when a step is difficult to reverse, financially significant, externally visible or based on uncertain AI output.

9. Agentic steps should be bounded inside the workflow

An agent can be one step inside a larger orchestrated system rather than the controller of everything.

Deterministic code may collect approved documents, then an agent may choose which permitted search tool to use, after which deterministic rules validate the result and decide whether human approval is required.

This mixed architecture gives AI flexibility where it helps while keeping permissions, state transitions and release decisions explicit.

Worked example: processing a customer refund request

Imagine a refund form is submitted on a website.

Form submitted
Validate order
Queue case
AI classifies reason
Rules check eligibility
Approve or escalate

The form submission is the trigger. Deterministic code validates the order number and stores the request.

A queued worker can ask an AI model to classify the customer's free-text explanation, but refund eligibility remains a rule-based decision based on policy and order data.

If the refund exceeds an approval threshold, the workflow pauses for a human decision before any payment action is attempted.

If a queue message is delivered twice, an idempotency key can help ensure the same refund case is not created twice.

Why this matters

Most useful AI products are not one model call. They are workflows containing ordinary software, external services, stored state and sometimes AI or agentic steps.

Understanding orchestration helps you decide where variability is acceptable and where the system must remain predictable.

It also prepares you for security and reliability: every trigger, tool, queue, credential and action creates a boundary that must be controlled.

Key terms

AutomationPredefined work that runs when a trigger or condition occurs.
OrchestrationCoordination of multiple workflow steps, services and decisions.
TriggerAn event or condition that starts a workflow.
WebhookAn HTTP-based event notification sent from one system to another.
QueueA buffer that stores work until a consumer is ready to process it.
RetryA later attempt to repeat an operation that failed.
IdempotentDesigned so repeating the same operation does not create an unintended additional effect.
BackoffWaiting progressively longer between repeated attempts.
