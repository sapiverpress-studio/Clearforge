Phase 1 · Day 15 · Security Boundaries

Security boundaries: secrets, permissions and prompt injection

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
Security is about controlling trust and limiting consequences. Treat external input as untrusted, keep secrets outside exposed client code, give each component only the permissions it needs, validate model outputs before acting, and design systems so one failure cannot reach everything.

1. Trust boundaries mark changes in trust

A trust boundary is a point where data, commands or authority move between components with different levels of trust.

User input, uploaded files, web pages, retrieved documents and third-party API responses should all be treated as potentially untrusted.

Crossing a boundary should trigger checks such as validation, permission enforcement and decisions about whether the data may influence later actions.

2. Secrets belong outside exposed client code

API keys, access tokens and database credentials are secrets.

If a private secret is embedded in JavaScript delivered to a browser, users can usually inspect and copy it.

Secrets should normally live in protected server-side storage or a secret-management system and be exposed only to components that need them.

3. Least privilege limits blast radius

Least privilege means granting only the minimum access required for a task.

An agent that only needs to read calendar events should not also be allowed to delete them.

Narrow permissions reduce the blast radius: the maximum damage one mistake or compromise can cause.

4. Prompt injection turns untrusted content into attempted instructions

A prompt injection occurs when crafted input causes a language model to behave in an unintended way.

It can be direct, from the user, or indirect, hidden inside external content such as a webpage, document or email.

The danger grows when the model can access tools or sensitive data, because manipulated output may influence real actions.

5. RAG does not make retrieved text trusted

Retrieval-augmented generation supplies external content to the model as context.

That content can still contain misleading data or hostile instructions.

RAG improves information access; it does not eliminate prompt injection or automatically turn external documents into trusted instructions.

6. Separate data from authority

User and retrieved content should be treated as data, not permission to change system rules.

The application should decide which instructions are authoritative and which material is merely evidence to analyse.

Because models can still be influenced by malicious content, external permission checks remain essential.

7. Model output is untrusted input to the next system

AI-generated text should not automatically be treated as safe code, SQL, shell commands, HTML or tool arguments.

If output drives another interpreter or action, validate it against the expected schema and enforce allow-lists or constraints where possible.

A model proposing an action is not the same as the system authorising that action.

8. Human approval can enforce a security boundary

For consequential actions, human approval separates a model recommendation from real-world execution.

The reviewer should see the proposed action and relevant evidence rather than a vague statement that “AI recommends this”.

Approval is particularly useful for irreversible, financial or externally visible actions.

9. Logging makes misuse visible

Logs and traces can record authentication events, tool calls, permission failures, unusual retries and unexpected data flows.

Monitoring does not prevent every failure, but it helps detect incidents, reconstruct what happened and improve controls.

Worked example: an agent reading supplier emails

Imagine an agent that reads supplier emails and drafts purchase-order updates.

Email arrives
Validate metadata
Model reads content
Extract changes
Rules validate fields
Human approves update

The email body is untrusted content and may include hostile instructions aimed at the model.

The model can extract a proposed quantity or delivery date, but ordinary software validates the fields and the agent receives no unrelated permissions.

The final purchase-order change can require approval. This design does not assume the model is impossible to manipulate; it limits what manipulation can achieve.

Why this matters

As AI systems gain retrieval, tools and automation, security becomes a system-design problem rather than a prompt-writing problem.

Safe architectures assume that models can be wrong, inputs can be hostile and credentials can be abused if exposed.

Good boundaries preserve useful capability while reducing the consequences of failure.

Key terms

Trust boundaryA point where data or authority crosses between different trust levels.
SecretA credential or sensitive value that must not be publicly exposed.
Least privilegeGranting only the access required for a specific task.
Blast radiusThe scope of damage possible from one failure or compromise.
Prompt injectionCrafted input that alters an LLM's behaviour in an unintended way.
Indirect prompt injectionInjection delivered through external content the model reads.
Output validationChecking generated output before another system uses it.
Allow-listAn explicit set of permitted values, operations or targets.
