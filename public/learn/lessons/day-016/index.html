Evaluation and testing

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
You cannot improve an AI system reliably unless you can measure what “good” means. Build representative test cases, define pass criteria before changing the system, compare against a baseline, and inspect failures at both the model level and the wider workflow level.

1. Evaluation begins with a defined task

Before measuring quality, define what the system is supposed to do.

“Give good answers” is too vague. A useful task definition states the input, expected behaviour, unacceptable failures and important constraints.

For example: “Given a customer email and approved policy, classify the issue type and identify whether human review is required.”

2. A test set should represent real work

An evaluation set is a collection of examples used to test performance.

It should include common cases, difficult cases, edge cases and known failure modes.

If all examples are easy, the test gives false confidence. If the examples do not resemble real usage, good scores may not translate into useful behaviour.

3. Define pass criteria before looking at results

A pass criterion states what counts as acceptable.

Some criteria are exact, such as “the extracted invoice number must match the source”. Others need judgement, such as whether a summary preserved the important facts.

Defining the criterion first reduces the temptation to move the goalposts after seeing the output.

4. Use a baseline to know whether a change helped

A baseline is the current system or a simpler reference approach.

When you change a prompt, model, retrieval method or tool configuration, compare the new version against that baseline on the same test set.

Without a baseline, “this feels better” is weak evidence.

5. Regression tests protect behaviour that already works

A change can fix one failure and create another.

A regression test checks that previously correct behaviour remains correct after a modification.

Useful AI evaluation therefore keeps examples from earlier bugs and reruns them whenever the system changes.

6. Separate model failure from system failure

When a result is wrong, identify where the failure occurred.

Was the wrong document retrieved? Was the correct tool unavailable? Did the model misunderstand clear evidence? Did deterministic code reject a valid result?

Calling every problem “the model failed” hides the real cause and leads to the wrong fix.

7. Automated metrics are useful, but limited

Some tasks allow straightforward automated scoring.

Classification can use accuracy, precision, recall or F1. Retrieval can use measures such as recall at k. Structured extraction can often be compared field by field.

Open-ended generation is harder because multiple answers can be acceptable. Automated judges can help, but important decisions should not rely on one opaque score alone.

8. Human review remains important for subjective quality

Humans are useful when quality depends on nuance, usefulness, tone, factual support or whether an answer actually solves the user's problem.

Reviewers need a rubric, not just “do you like it?”.

A rubric might score factual support, completeness, harmful errors and clarity separately.

9. Production monitoring is part of evaluation

Pre-release tests cannot cover every real input.

After deployment, systems should monitor failure rates, latency, tool errors, cost, user corrections and other signals relevant to the task.

Real failures can then become new test cases, making the evaluation set stronger over time.

Worked example: evaluating a policy-answering assistant

Suppose you build an assistant that answers staff policy questions using RAG.

Create test questions
Record expected sources
Run retrieval
Generate answers
Score evidence use
Add failures to tests

A strong evaluation separates retrieval and generation. First ask whether the correct policy passage appeared in the retrieved context. Then ask whether the final answer accurately used that passage.

If retrieval fails, improve indexing or search. If retrieval succeeds but the answer is wrong, inspect prompting, model behaviour or answer validation.

This turns evaluation into diagnosis rather than a single score.

Why this matters

AI systems are probabilistic and can change when prompts, models, tools or data change.

Evaluation gives you a controlled way to detect whether those changes improve reliability or create regressions.

It is the bridge between experimentation and dependable product behaviour.

Key terms

Evaluation setA collection of representative examples used to test system performance.
Pass criterionA predefined rule describing what counts as acceptable performance.
BaselineA reference system used for comparison.
Regression testA test that checks whether previously working behaviour still works after changes.
MetricA numeric measure summarising some aspect of performance.
RubricA structured set of criteria for human or model-based judging.
Failure modeA recurring pattern in which the system produces an undesirable result.
Production monitoringTracking real-world performance after deployment.
