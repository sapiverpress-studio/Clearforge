Cost and latency in AI systems

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
AI quality is only one engineering objective. Real systems also have budgets and response-time targets. Cost and latency come from the whole workflow: model choice, input size, output length, retrieval, tool calls, retries and how often repeated work can be avoided.

1. Cost is generated by work performed

AI APIs usually charge according to some measure of usage, such as input tokens, output tokens, generated media, compute time or tool use.

The exact pricing model varies by provider and product, so architecture should not depend on one permanent price assumption.

The useful engineering question is: what work is the system performing, how often, and which parts are actually necessary?

2. Input and output tokens affect price and speed

Longer prompts require more tokens to be processed. Longer answers require more tokens to be generated.

That can increase cost and often increases latency too.

Good context engineering includes removing irrelevant material, not merely adding more context just in case.

3. The largest model is not automatically the best model

Different models trade capability against price, latency and resource use.

A complex reasoning task may justify a more capable model, while simple classification or extraction may work well with a smaller, faster option.

Evaluation from Day 16 makes this decision defensible: choose the cheapest and fastest option that still meets the required quality threshold.

4. Latency has several components

User-visible response time is not just model generation time.

It can include network delay, authentication, database queries, retrieval, model processing, tool calls, retries and rendering.

Measure the stages separately. Otherwise a slow database lookup can be mistaken for a slow model.

5. Time to first token and total time are different

For streamed text generation, users may see output before the full response is finished.

Time to first token measures how long the user waits before generation becomes visible. Total latency measures the complete end-to-end duration.

A system can therefore feel responsive even when the complete generation takes longer.

6. Caching avoids repeating identical work

A cache stores a previously computed result so it can be reused.

Caching can reduce repeated API calls, latency and cost when the same or equivalent request occurs again.

Cached data can become stale, so the system needs a rule for expiry or invalidation.

7. Batching improves throughput when immediacy is unnecessary

Batching groups multiple pieces of work so they can be processed together or asynchronously.

This is useful for jobs such as classifying thousands of records, generating embeddings for a document collection or running evaluation suites.

Batching may reduce overhead or cost, but it is unsuitable when a user needs an immediate interactive response.

8. Parallel work can reduce latency but increase resource use

Independent operations can sometimes run at the same time.

An application might retrieve account data and product documentation in parallel instead of waiting for one request before starting the other.

Parallelism can reduce wall-clock time, but it may increase concurrency, complexity and cost.

9. Retries and agent loops can multiply cost

One user request can trigger many hidden operations.

An agent might call several tools, retrieve documents, retry failed requests and invoke a model multiple times.

Cost should therefore be measured per completed task, not only per individual model call. Step limits and stopping rules are also cost controls.

Worked example: a support assistant

Imagine a support assistant that receives a customer question.

User request
Classify intent
Retrieve evidence
Generate answer
Validate result
Return response

The first version uses a large model for every stage and sends far more context than needed. It works, but it is slow and expensive.

A better design may use deterministic rules or a smaller model for intent classification, retrieve only relevant passages, reserve the stronger model for difficult cases and cache stable information.

The correct optimisation is not “make everything cheaper”. It is “remove waste while preserving the quality threshold”.

Why this matters

A technically impressive AI feature can still fail as a product if every interaction is too expensive or too slow.

Evaluation tells you the minimum quality required. Cost and latency engineering help you reach that quality efficiently.

Key terms

LatencyThe elapsed time between starting a request and receiving the required result.
Time to first tokenThe delay before the first streamed model output becomes visible.
ThroughputThe amount of work a system can process over a period of time.
CacheStored output reused to avoid repeating the same computation or request.
Cache invalidationThe process of removing or refreshing cached data that is no longer valid.
BatchingGrouping multiple jobs for combined or asynchronous processing.
ParallelismRunning independent operations at the same time.
Quality thresholdThe minimum acceptable performance established through evaluation.
